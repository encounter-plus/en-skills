# Правила версионирования для агента

## Область версий

- `package.json.version` — версия пакета инструментов и поставляемых skills/knowledge. Изменение поведения через инструкции считается изменением продукта, даже если TypeScript не менялся.
- `runtime/package.json.version` — независимая версия MCP runtime, его инструментов, схем и поведения импорта.
- При изменении обоих компонентов повышай обе версии. Совпадение их номеров не требуется. Сборка en-agent получает эти значения как `skillsVersion` и `mcpVersion`; версия самого комплекта определяется в en-agent.
- Синхронизируй версии пакетов с соответствующими записями существующих lock-файлов. Сгенерированные файлы обновляй сборкой из исходников.

## Выбор следующей версии

| Изменение поставляемого компонента | Повышение |
| --- | --- |
| Исправление без нарушения контракта, уточнение инструкции с сохранением возможностей | PATCH |
| Новая совместимая возможность, инструмент или необязательный параметр | MINOR |
| Удаление/переименование инструмента, новый обязательный параметр, несовместимый результат или формат сохранённых данных | MAJOR для 1.x и выше; MINOR для 0.x с явным описанием несовместимости |
| Только тесты, комментарии или документация разработчика, не входящая в инструкции продукта | Версию сохраняй |

Повышай самый значимый разряд из затронутых изменений, младшие разряды обнуляй. Одного повышения на совокупность изменений выпуска достаточно: не повышай версию на каждый файл или коммит. Уже выпущенную версию с другими байтами повторно не распространяй. Если неизвестно, была ли версия распространена, проверь историю выпусков и доступные манифесты; перед новой поставкой выбери новый номер.

## Порядок работы

1. До редактирования проверь текущие версии и накопленные изменения; определи затронутые компоненты и совместимость.
2. Для обычной разработки укажи требуемое повышение в результате работы. Перед упаковкой для передачи, установкой или публикацией примени повышение к исходным манифестам и lock-файлам. Если номер уже поднят для этого ещё не выпущенного набора изменений, повторное повышение не требуется.
3. Пересобери пакет и skills, выполни `npm run check`; при изменениях runtime выполни также его `validate`. Проверяй ссылки внутри упакованных skills. Используй синтетические данные.
4. При включении в en-agent проверь, что его манифест содержит фактические версии обоих компонентов и хеши новых файлов. Изменение вложенного компонента требует нового ID комплекта по правилам en-agent.
5. В результате укажи старые и новые версии, совместимость и выполненные проверки. Отделяй подготовленный исходный код от собранного, установленного и опубликованного выпуска.

Смена номера не заменяет миграцию данных. Несовместимое изменение журнала, плана или контракта требует проверенного перехода либо явного отказа с понятной ошибкой. Изменения инструкций не дают разрешения изменять реальную игру. Установка и публикация требуют явного запроса пользователя.
