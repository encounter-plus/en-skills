# Проверки поведения агента

cases.json (schemaVersion 2) — единый каталог сценариев, не результатов. Для настоящего прогона дайте агенту пользовательский запрос, установленный skill и минимальные синтетические исходники. Поле checks оставьте оценщику, чтобы оно не подсказывало ответ.

Случаи `mechanics-*` покрывают обычные и множественные эффекты ответа, замены, бонусные окна, запечатанный реквизит, технические подсказки, версии источников, дуали, профили, покрытие связи, резерв поля и смысловое оформление. [Форматы синтетических исходников](fixtures/scenario-mechanics/README.md): внутренний GameDraft либо отдельные wire bodies нового API, проверенные по включённому фрагменту OpenAPI. Описание замысла в request остаётся авторским вводом; оно не становится произвольными полями API. Не используйте старый HTML-экспорт как DTO нового движка.

Для фото нужен подготовленный набор изображений с известной надписью и разрешением на использование; текстовое описание фото не доказывает vision. Сохраните версию skill/model, вход, результат, tool trace, использованные токены, время и результат каждого критерия. Сравните с агентом без skill или предыдущей версией. Ошибочные изменения кодов и недоказанные заявления об успешной записи — отдельные провалы.

## Подготовка и исполнение

Из корня репозитория:

```sh
npm run validate:evals
npm run eval:prepare -- audit-author-intent .tmp-eval/agent .tmp-eval/evaluator
```

Каждая подготовка использует новые каталоги; существующие файлы не перезаписываются. Каталог оценщика должен находиться вне каталога агента. Подготовка собирает автономные skill-пакеты прямо из исходников, сохраняет хеш точных байтов и исходного запроса с fixtures. Для baseline выполняйте её на сохранённом рабочем дереве до правок, включая незакоммиченные изменения, а не на старом HEAD.

Агент получает только input.json и skills/. Fixtures передаются base64 с исходным путём: декодируйте их без преобразования содержимого и показывайте изображения как реальные изображения. В explicit/dialogue режиме предоставлен выбранный skill; `availableSkills` добавляет необходимые соседние workflows, например level-author для проверки перехода из game-author. Этот состав входит в inputHash. В routing предоставлены все skills; host показывает их метаданные для выбора, не загружает все тела инструкций и не сообщает expectedSkill. Для проверки router явно выберите game-author в запросе explicit случая.

Evaluator получает rubric.json: ожидаемый процесс, критерии и последующие пользовательские реплики. В dialogue режиме отправляйте turns по одной после ответа агента; последующие реплики и rubric заранее агенту не показывайте. Сохраняйте весь разговор. Метаданные origin описывают происхождение: synthetic либо обезличенный incident с источником. Синтетические примеры не называются наблюдавшимися инцидентами.

Пустой tools означает отсутствие сервисных инструментов. Чтение предоставленных локальных skill/fixture-файлов разрешено. Случаи с намеренным отсутствием доступа оценивают честный ограниченный результат. Для положительных интеграционных прогонов нужно отдельно предоставить синтетические инструменты и обновить контекст случая; не обращаться к настоящей игре. Ожидание, которое невозможно проверить в данных условиях, получает not-checked либо fail, но не выдуманный trace.

Для локального Codex CLI есть host-адаптер `tooling/eval-run-codex.mjs`, затем независимый оценщик `tooling/eval-judge-codex.mjs`. Они не входят в npm-поставку и используют авторизацию установленного CLI, не копируют credentials в fixtures. Запуск отправляет материалы модели: согласуйте внешнюю передачу приватных материалов перед запуском. Подготовка файлов не считается модельным прогоном.

Оба скрипта принимают путь к JSON-конфигурации: `root`, `baseline` (сохранённые исходные skills/knowledge), `out` (новый каталог), `cliEntry` (абсолютный путь к установленному `@openai/codex/bin/codex.js`), `cliVersion`, `model`, `repetitions: 3`, необязательные `concurrency` и `judgeConcurrency`. `caseIds` ограничивает выборку; для полного прогона не задавайте его. Каталог кейсов по умолчанию берётся из root, а исходники baseline — из baseline: изменения схемы eval не меняют тестовые входы одной стороны.

Для продолжения зафиксированного эксперимента `catalogPath` задаёт сохранённый каталог кейсов. `sides: ["baseline"]` либо `["candidate"]` позволяет закончить одну сторону отдельно после исправления другой. Новая ревизия skills требует нового out; исполнитель проверяет хеши подготовленных входов и bundle, при возобновлении также сверяет хеш исходного trace. `retryPartial: true` сохраняет неполную попытку и создаёт вложенный retry (не более трёх). В итоговый набор включайте одну проверяемую ревизию каждой стороны, одинаковые входы/рубрики и все повторы; исключённые из-за ошибки окружения попытки сохраняйте с объяснением.

Адаптер сохраняет отдельные prompt, stderr, исходный JSONL, финальный ответ и метрики каждой реплики. В dialogue последующие реплики передаются по одной с историей уже завершённых ответов и инструментов (replay в новом контексте, не native resume). У обеих сторон одинаковый read-only shell без сервисных инструментов, сетевого поиска и глобального каталога skills. Ограничение чтения каталогом задачи задаётся инструкцией; read-only sandbox сам по себе не запрещает чтение всех остальных файлов. Оценщик должен отмечать выход за границы. Незавершённые журналы не считаются pass, исходные попытки не перезаписываются. Оценка проводится в отдельном контексте со скрытыми названиями сторон; она также сохраняет собственный полный trace.

Формат JSONL и параметры CLI: [официальная документация](https://learn.chatgpt.com/docs/non-interactive-mode). Прежде чем использовать другую версию CLI, проверьте совместимость экспорта. Полнота trace означает полноту наблюдаемых событий инструментов, а не доступ к скрытым рассуждениям модели.

Оценщик создаёт нейтральный рабочий каталог с непрозрачным ID: названия baseline/candidate отсутствуют и во входных путях, и в cwd. Маскируются только пути workspace, а не буквальные строки ответов. `judgeWorkspaceRoot` позволяет выбрать корень этих каталогов. Полный trace доступен оценщику рядом с кратким обзором; после оценки входы и журнал копируются в `judging-blind-v1-*` для проверки происхождения вердикта.

Если обнаружена ошибка критерия, сохраните прежний каталог, задокументируйте причину и передайте одинаковый исправленный `rubricCatalog` обеим сторонам. Оценщик разрешает повторную оценку только при неизменном inputHash: изменение запроса или fixtures требует новых ответов обеих сторон. Старые оценки сохраняются отдельно. Не меняйте критерии ради успешного результата.

`node tooling/eval-assemble.mjs CONFIG.json` собирает окончательную выборку. Конфигурация содержит `root`, каталоги `baseline` и `candidate`, новый `out`, при необходимости `baselineOverrides`/`candidateOverrides` — отображения caseId в каталоги повторно выполненных случаев. Сборщик требует ровно три повтора каждого случая текущего каталога, единую ревизию bundle каждой стороны, одинаковые входы/критерии и полные исходные JSONL исполнения и слепой оценки. Он сохраняет before/after/comparison и sources с SHA-256 исходных файлов; при неполной выборке ничего не публикует. Замены условий фиксируйте по причинам ошибок входа или окружения, не по качеству ответа.

## Формат результата

Для сравнения подготовьте два JSON-массива элементов `{ "result": ..., "rubric": ... }`; rubric берётся из подготовки соответствующего набора, не переписывается под ответ. Минимальный result:

```json
{
  "schemaVersion": 1,
  "caseId": "audit-author-intent",
  "inputHash": "hash-from-preparation",
  "bundleHash": "hash-from-preparation",
  "runId": "candidate-1",
  "model": "exact-model-and-reasoning-setting",
  "host": "host-and-version",
  "toolset": "synthetic-tools-version",
  "answer": "Actual final answer",
  "dialogue": [{"role":"user","content":"Actual request"},{"role":"assistant","content":"Actual answer"}],
  "evaluator": "independent-reviewer",
  "tokens": null,
  "durationMs": null,
  "writeClaim": "none",
  "trace": {"complete": false, "source": "unavailable", "events": []},
  "checks": [{"index":0,"status":"not-checked","evidence":"Reason or exact evidence"}]
}
```

В checks нужна запись для каждого критерия rubric в исходном порядке, с index от нуля. Статусы: pass / fail / not-checked. Оценщик изучает запрос, материалы, весь разговор и trace; поиск слов в ответе не заменяет смысловую оценку. writeClaim отражает заявление в ответе: none / verified / partial / unknown. Неизвестные метрики записываются null, не нулём.

Нормализованные trace.events сохраняют порядок исходного экспорта:

- `read-reference`: path фактически прочитанного файла.
- `select-skill`: skill фактически выбранного/прочитанного процесса; простое упоминание не подходит.
- `mutation`: operationId уникальной попытки и answerStrings всех переданных строк ответов, без нормализации.
- `read-back`: operationId той же попытки и matches по независимому чтению нужных значений после неё.

Храните исходный экспорт рядом и указывайте его в trace.source. complete=true допустимо только для полного журнала инструментов. Пересказ агента о прочитанных файлах не является полным trace. Assertions проверяют отсутствие мутаций, выбранный skill, нужные чтения, разрешённые точные строки и read-back после заявления verified. Они не доказывают подлинность поданного журнала; это обязанность host/оценщика. Без полного trace итог не будет pass.

```sh
npm run eval:compare -- .tmp-eval/before.json .tmp-eval/after.json
node tooling/eval-report.mjs .tmp-eval/before.json .tmp-eval/after.json .tmp-eval/report.md
```

Сравнимость требует одинаковых caseId/inputHash/model/host/toolset, критериев и числа повторов. Для изменённых случаев выполняйте по три независимых повтора до/после. Непарные условия выводятся отдельно; CLI возвращает ненулевой код при несравнимости, менее трёх повторах или непрошедшем candidate. Для каждого случая рассматривайте все оценки, а не только итоговую долю. Сохранность кодов, разрешений и достоверность успеха обязательны; снижение стоимости контекста не компенсирует их провал.

## Что проверяет обычный check

npm run check включает структуру каталога и детерминированные тесты подготовки/сравнения. Эти тесты используют искусственные журналы и доказывают поведение проверяющего кода, не модели. Полный модельный прогон, vision и реальные платформы остаются отдельными результатами.
