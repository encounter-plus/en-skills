# Приоритет экранов для авторского UI

Перед проектированием определите поверхность (задание или анонс), тип игры и явно заданные автором целевые устройства. Для выбора приоритета используйте тип игры, а не порядок прохождения уровней: штурмовая последовательность сама по себе не означает тип «Мозговой штурм». Если тип неизвестен, уточните его у автора.

| Поверхность и тип игры | Приоритет | Как проектировать |
| --- | --- | --- |
| Скрипт задания: «Мозговой штурм» | Desktop first | Сначала продумайте работу на широком экране с мышью и клавиатурой; затем адаптируйте интерфейс для телефона. |
| Скрипт задания: остальные типы, включая «Схватку» и «Точки» | Mobile first | Сначала спроектируйте узкий экран и сенсорный ввод; затем расширяйте компоновку для desktop. |
| Анонс игры, включая его скрипты: любой тип игры | Mobile и desktop обязательны | Содержание и все действия должны работать на обеих поверхностях; тип игры не отменяет эту проверку. |

First определяет порядок проектирования и основной сценарий использования, а не отказ от второй платформы. Если автор явно задал другой приоритет, следуйте ему и зафиксируйте это в результате.

## Проверка результата

Проверяйте читаемость, размещение элементов, ввод и основные действия на узком и широком экране. Управление должно работать касанием, мышью и клавиатурой; существенные действия и сведения доступны без hover. Проверьте отсутствие непреднамеренной горизонтальной прокрутки и перекрытия полей экранной клавиатурой на доступном устройстве. В отчёте укажите приоритет, размеры экранов, способы ввода и непроверенные сценарии.

Для задания используйте [настоящую /preview Encounter и отдельный EN+ bridge](script-harness.md). Анонс — это авторский HTML-блок на странице игры `/games/{gameId}`, а не отдельная страница. Проверяйте его внутри страницы игры на mobile и desktop, а для приложения — в полном описании игры. Успешный тест в gameplay не подтверждает работу анонса. Доступность `window.EN`, селекторов и других API на этой поверхности устанавливается отдельно по [контракту и ограничениям](scripting-contract.md).

## Общее оформление через CSS

Для нового или изменяемого оформления заданий используйте CSS-классы вместо повторяющихся inline-стилей. Цвета выделений, фон, полосу слева, отступы и оформление иконок храните в общем CSS-файле игры с префиксом классов, ограничивающим действие авторскими блоками. Основание и место подключения — OPS-23 в [руководстве автора](authoring-guide.md).

1. Прочитайте действующие стили и сообщение автора/организатора, используемое для оформления. Сохраните существующие подключения, текст, скрипты и настройки показа. Проверьте, что сообщение охватывает нужные уровни; изменение его видимости требует соответствующего разрешения.
2. В согласованном объёме замените атрибуты style классами, перенеся их декларации без изменения смысла и внешнего вида. Для стилей, которые меняет скрипт, нужна отдельная проверка: не ломайте динамическое поведение ради удаления всех атрибутов. Массовый перенос старого оформления выполняйте только по запросу.
3. Загрузите обновлённый CSS в файлы игры и подключите его через это сообщение, например link rel="stylesheet". Сначала подтвердите доступность ресурса и подключения, затем сохраняйте зависимые тексты. Выберите подтверждённый способом хостинга вариант обновления кеша; новое имя файла допустимо. Не обещайте мгновенное обновление прежнего URL.
4. Проверьте повторным чтением текст сообщения, URL и классы, затем фактическое применение новой версии CSS на узком и широком экране. Успех загрузки файла не доказывает его применение; преждевременное чтение размеров изображения не доказывает несовместимость формата. Отдельно укажите непроверенные приложение/браузер.

Анонс — отдельная поверхность: не предполагайте, что сообщение уровня подключает CSS на странице анонса. Подключение и проверку этой поверхности выполняйте отдельно в разрешённом объёме.

## Автоперенос строк в legacy engine

Галка «включить автоперенос строк» управляет преобразованием текста при отображении: если она включена, legacy engine заменяет реальные переводы строк `\n` на HTML-теги `<br>`. Имеется в виду символ перевода строки, а не буквальный текст `/n` или `\n`. В редакторе исходные переводы строк сохраняются. При выключенной галке автоматическая подстановка `<br>` не выполняется; переносы задаются авторской HTML-разметкой и CSS.

Через SDK/инструменты передавайте булевый `replaceNlToBr`; legacy-адаптер передаёт его как `replace_nl_to_br` и устанавливает соответствующую галку нативной формы. Например, `replaceNlToBr: true` включает автоперенос, `replaceNlToBr: false` выключает. Для создания задания значение задаётся явно; при обновлении отсутствие параметра сохраняет прежний режим. Чтение задания возвращает `_authoring_replace_newlines`, сообщения — `replace_nl_to_br`. Передавайте исходный текст с переводами строк: вручную заменять их на `<br>` одновременно с включением флага не нужно.

Это описание преобразования относится только к **legacy engine**. Наличие одноимённого поля в modern DTO само по себе не подтверждает такое поведение modern engine.

При переносе оформления в общий CSS сохраняйте существующее значение галки, если изменение режима не входит в задачу. Для многострочного HTML учитывайте, что включённый автоперенос добавляет видимые разрывы строк; после сохранения проверьте и исходный текст с флагом, и фактическую разметку в предпросмотре.
