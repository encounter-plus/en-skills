# Уровень из чата: соответствие административной модели

Эта карта нужна при подготовке черновика и перед переносом в движок. Предметная модель — в [encounter-domain.md](encounter-domain.md), общие правила записи — в [admin-contract.md](admin-contract.md).

Источник сверки: `encounter-api-sdk/spec/upstream/swagger.json`, происхождение в соседнем `source.json`: `https://api.en.cx/swagger/doc.json`, fetchedAt `2026-10-07T00:15:28.153Z`. Это локальный снимок Swagger 2.0, не результат live-проверки. Имена ниже — JSON wire fields; SDK может использовать другой регистр имён. При доступном новом контракте сверяйте отличия до записи. Для установленного скилла наличие checkout SDK не требуется: карта переносится вместе с ним.

## Создание, удаление и копирование уровня

`encounter_propose_level_operation` готовит карточку с `action: create | delete | copy`, `count` для создания/копирования и постоянным `levelId` для удаления/источника копии. Для нового modern-уровня используйте `count: 1`; native modern create выполняет один запрос, поэтому несколько уровней создавайте отдельными подтверждёнными карточками. Legacy create и native copy допускают 1–20. Копирование выполняется внутри выбранной игры. В [локальном runtime](mcp-runtime.md) те же действия доступны как CLI `create-level`, `delete-level`, `copy-level` (`encounter-agent operation <имя> --input private-input.json`) и MCP `encounter_create_level`, `encounter_delete_level`, `encounter_copy_level`. Вход содержит `gameId`, для удаления/копии — постоянный `levelId`, для создания/копии — `count`; запись требует `confirmed: true` после согласования конкретного действия. Карточка фиксирует инвентарь и версию; перед записью перечитывается весь список, после записи сверяются новые постоянные ID и порядок. Это наблюдаемая версия, а не серверный CAS структурных операций.

Создание добавляет пустой уровень в конец; настройка названия, задания, секторов, подсказок и позиции — отдельные проверяемые шаги. Legacy `move` принимает постоянные `levelId` и `afterLevelId`. Для modern вставка в середину этим инструментом не поддержана: не объявляйте согласованную позицию выполненной. Удаление убирает весь уровень и его содержимое; `levelId=0`/«удалить все» не поддержаны. Снятие/восстановление — отдельные `dismiss`/`restore`, которые сохраняют уровень; не заменяйте снятие удалением.

`copy` вызывает native copy движка и возвращает новые ID. Подтверждённый инвентарь ещё не доказывает полноту содержимого копии: перечитайте editor источника и каждого нового уровня, проверьте задания, адресатов, настройки, ответы, подсказки, бонусы и глобальные ссылки. До такой сверки сообщайте «native copy выполнено, состав требует проверки», а не «уровень готов». Не нормализуйте строки ответов. Не повторяйте действие после неизвестного исхода; сначала выполните чтение и сверку.

## Поля и операции

Базовый путь уровня: `/admin/games/{id}/levels/{levelId}`. В таблице пути с начальным `/` после имени операции — суффиксы этого пути, кроме явно указанного создания уровня.

| Часть черновика | Контракт снимка | Что проверить |
|---|---|---|
| Создать уровень | `POST /admin/games/{id}/levels`, `models.AdminCreateLevelRequest`: `level_name`, `comment`, `after_level`, `before_level`; ответ `AdminLevelItem` | Позицию согласовать и проверить значение ссылок before/after в adapter: снимок не уточняет, ID это или номер. Получить настоящий `level_id`; создание уровня ещё не создаёт весь его контент. |
| Прочитать | `GET /editor`, `AdminLevelEditorResponse`: `level`, `tasks`, `helps`, `penalty_helps`, `sectors`, `answers`, `bonuses`, `version` и настройки | `level.level_name` — название; `level_id` и `level_number` различны. Читать capabilities `supports_*`, `bonuses_supported`, `penalty_helps_supported`, `can_edit_auto_pass` и live state. |
| Название | `PUT /meta`, `AdminLevelMetaRequest.level_name`, `comment` | Не подменять названием поле `task_text` и не очищать существующий служебный комментарий. |
| Текст | `AdminTaskRequest`: `task_text`, `for_member_id`, `latitude`, `longitude`, `replace_nl_to_br` | ФО входит в видимый `task_text`. В этом DTO нет отдельного поля ФО. `for_member_id=0` означает всех; существующих адресатов сохранять. Уровень может содержать несколько tasks. |
| Автопереход | `PUT /autopass`, `AdminLevelAutoPassRequest`: `timeout_hours/minutes/seconds`, `penalty_enabled`, `penalty_hours/minutes/seconds`, `award_is_penalty`, `points_award` | Чтение: `timeout_sec`, `timeout_time_award_sec`, `timeout_points_award`. Согласовать штраф отдельно от таймаута. Способ отключения и знак начисления проверять по adapter; поле enabled для автоперехода в DTO отсутствует. |
| Сектор | `AdminSectorRequest`: `sector_name`, `task_id`, `valid_answer_score_award`, `wrong_answer_score_penalty` | Привязать сектор к правильному task; счётные настройки нужны только для соответствующей механики. |
| Ответ сектора | `AdminAnswerRequest`: `answer_text`, `sector_id`, `for_member_id`, `score_award`, `time_award` | Альтернативные строки одного ответа принадлежат одному сектору. Сохранять точные значения; варианты не увеличивают число секторов. |
| Все или K из N | `PUT /settings`, `AdminLevelSettingsRequest`, `section=sectors`, `required_sectors_count` | В снимке `0 = all sectors`; K должно быть достижимо при фактических N секторах. Другая секция `pass_rule` содержит `passing_condition_id`, `required_answers_num`, `required_points`, `complete_type_id`, `pass_limit`; не заменять ей настройку sectors по догадке. В editor `passing_condition_id`: 0 все секторы, 1 заданное число, 2 очки. Выбирать правило по типу игры и capabilities. |
| Подсказка | `AdminHelpRequest`: `help_text`, `timeout`, `for_member_id`, `is_penalty`, `penalty_time`, `penalty_score`, `penalty_comment`, `request_penalty_confirm` | В тексте черновика время от старта уровня с единицами. Снимок не задаёт единицы `timeout`/`penalty_time`; конверсию подтверждает adapter, а не название поля. Штрафная подсказка отличается от штрафа автоперехода. |
| Бонус | `AdminBonusRequest`: `bonus_name`, `task`, `answers[]`, `bonus_time`, `negative`, `bonus_help` | Текст задания бонуса — `task`, кандидат на текст после выполнения — `bonus_help`; его фактический момент показа проверить в adapter/preview. Единица `bonus_time` и семантика `negative` не описаны в снимке; не выводить их из названия. Награду другого типа не кодировать произвольным полем. |
| Доступность бонуса | `all_levels`, `level_ids`, `for_member_id`, `has_delay`, `delay_sec`, `has_relative_limit`, `life_time_sec`, `has_absolute_limit`, `valid_from`, `valid_to` | Бонус «на этом уровне» не должен случайно стать общим. Абсолютные даты требуют часового пояса; ограничения и адресатов включить в черновик. |
| Блокировка | `PUT /settings`, `section=blocking`: `attempts_number`, `attempts_period_hours/minutes/seconds`, `block_type_id` | Editor возвращает `attempts_period_sec`; `block_type_id`: 1 пользователь, 2 команда. Какие попытки учитываются, условия снятия и способ отключения должен подтверждать adapter. Интервал учёта попыток сам по себе не доказывает длительность отдельной блокировки. |
| Общий лимит ответов | `section=restriction`: `restriction_enabled`, `attempts_count`, `unrestricted`; editor `answer_limit` (`-1 = unrestricted`) | Это отдельная настройка, не блокировка частоты. Не отправлять read-поле `answer_limit` вместо write-полей. |

`duration_sec`/`duration_hours/minutes/seconds` относятся к отдельной поддерживаемой настройке длительности. Плановое время решения из интервью не является командой её включить. Поля quiz-настроек не становятся настройками обычной «Схватки» только потому, что присутствуют в общей модели.

## Перенос согласованной версии

1. Проверьте инструменты хоста отдельно для создания уровня, meta, autopass, settings и содержимого. Наличие маршрута в Swagger не означает наличие callable tool. [Локальный MCP](mcp-runtime.md) имеет более узкий набор операций; не выдумывайте `encounter_create_level`. Сначала закончите черновик, затем сообщите точное отсутствующее действие, если оно мешает записи.
2. Прочитайте игру, список уровней, editor существующей цели и live-состояние. Сопоставьте понятные автору значения с DTO и единицами; сохраните исходные значения, версию и адресатов. Разрешите неоднозначности до отправки. Проверка неизвестной семантики на реальной игре записью не является допустимым экспериментом.
3. Для нового уровня после согласования создайте его один раз, получите ID и свежий editor. Зависимые сущности привяжите к полученным ID. Для существующего используйте устойчивые ID; совпадение названия не разрешает создавать дубликат.
4. Для содержимого используйте подтверждённые отдельные CRUD-операции или version-bound `POST /apply` с `base_version` и `ops`. Apply поддерживает `task`, `help`, `penalty_help`, `bonus`, `sector`, `answer`; meta/settings/autopass — отдельные операции. Нет одной общей транзакции для всего уровня. В apply `tmp_id` есть, но формат ссылок внутри слаботипизированных `fields` требует проверенного adapter. При отдельных запросах сначала создайте родителя, затем используйте его возвращённый ID.
5. Учитывайте правила [admin-contract.md](admin-contract.md): максимум 200 ops, ограничения при игроках, устаревшую версию, частичное применение. После каждой влияющей на версию операции читайте свежую базу для следующей зависимой записи; если состояние изменилось чужими правками, пересоберите diff, не переносите старое согласие на новый результат.
6. При ошибке остановите зависимые записи и перечитайте состояние. Не повторяйте неизвестный create; частично созданный уровень не удаляйте автоматически. Укажите конкретные созданные ID, применённые части и остаток. Возобновление начинается с сверки, а не повторной отправки всего плана.
7. После завершения перечитайте editor и проверьте все согласованные поля и связи, отдельно результат meta/settings/autopass. При доступном preview проверьте видимый текст, ФО, подсказки и бонусный Help; read-back не доказывает фактический момент показа игрокам. Отделите сохранение от непроверенного поведения.

Человеческий черновик — спецификация намерения, не готовый API payload. Разрешённая запись определяется согласованным содержимым, свежим состоянием и возможностями хоста одновременно.

## От черновика к заполнению

Черновик пригоден для обсуждения с явно указанными неизвестными. К заполнению переходите после согласования полной версии и проверки поддержки всех согласованных частей. Повторное чтение сверяет тот же реестр, включая сохраняемые значения. Новая проверка полноты не требует повторного одобрения неизменённого уже разрешённого плана.
