# Пользовательские HTML/CSS/JavaScript и preview

Статический просмотр исходника не доказывает работу авторского скрипта. Проверяй его в браузере внутри фактического документа движка.

## Правильность кода: локальное сравнение

Если исходник — полевая надпись, сначала выдели вводимый ответ по [глоссарию](glossary.md): отдели установленный префикс и служебные обозначения, сохрани античит и покажи преобразование. Это интерпретация исходника, а не дополнительная нормализация сравнения. Готовый код сравнивай буквально по правилу ниже. Совпадение с проверочным бонусом отмечай как проверку чтения отписки, а не как решение задания; это не основание отправлять код в игровую форму.

Если нужно узнать, есть ли код среди ответов уровня, получи полный JSON уровня через авторский API и сравни строки локальным скриптом: `candidate.trim().toLowerCase() === answer.trim().toLowerCase()` для обеих сторон. При наличии инструмента локальной проверки используй его; не выдавай догадку модели за результат скрипта.

- Сначала установи домен, игру и уровень; номер уровня не подставляй вместо его API ID.
- Проверяй ответы уровня/секторов и ответы бонусов, сохраняя назначение игроку/команде и признак штрафного бонуса в результате. Не считай индивидуальное совпадение подходящим всем участникам.
- Сохраняй ведущие нули и внутренние пробелы. Не удаляй пунктуацию, не заменяй похожие символы и не используй нечёткое сравнение.
- Используй полные данные, а не сокращённый текст для модели. При недоступных, неполных или усечённых данных сообщи, что проверка не завершена; не объявляй код неверным.
- Для этой проверки не отправляй код ни в игровую форму, ни в preview, ни в API отправки ответов. API нужен только для чтения JSON; проверяемый код в запрос чтения не включается.
- Отчёт содержит найденные совпадения и их назначение. Совпадение строки не доказывает доступность бонуса по времени, отсутствие блокировки ввода или прохождение уровня.

## Реакция скрипта: сценарий в preview

Профиль задаётся host: demo.en.cx — modern/Kotlin, остальные разрешённые Encounter domains — legacy/RN. Legacy preview: `/admin/games/levels/preview/{gameId}?level={number}`; используйте соответствующий профилю controller. [Выбор runtime](scripting/common.md) и [границы проверки](scripting/validation.md).

Для проверки отображения и поведения скрипта используй фактическое авторское preview. Синтетический пример (перед запуском замените ID на свою разрешённую тестовую игру): `https://demo.en.cx/admin/games/900001/levels/preview/9` — домен `demo.en.cx`, игра `900001`, превью уровня `9`. Обычный адрес `/games/{id}` не означает preview. Авторская страница редактора также не является формой проверки ответов.

Частый сценарий задания: ввод кода бонуса открывает его Help с HTML/JS; скрипт из Help выполняется и заменяет содержимое задания. Локальное сравнение кодов этот сценарий не проверяет.

1. Зафиксируй исходный текст, оформление, изображения и ожидаемое изменение в нужном уровне preview.
2. Введи тестовый код через штатную форму preview только для воспроизведения сценария скрипта, используя разрешённые инструменты среды. Если ввод доступен только автору через кнопку, попроси выполнить этот шаг; не утверждай, что отправил код сам.
3. Дождись появления бонусного Help и изменения DOM. Перечитай текст, стили и состояние изображений; сравни ожидаемое изменение с фактическим. Для отложенного результата перечитывай страницу без повторной отправки кода.
4. Отдельно укажи наблюдаемую реакцию и непроверенные части. Не повторяй отправку автоматически при неизвестном результате. Не переноси сценарий на игровой движок.

Настоящий runtime проверяется через `en-engine-check --url ...`. [Формат сценария и границы](script-harness.md). Сначала сохраните новый HTML в игре: этот путь проверяет уже сохранённый уровень. EN+ проверяется отдельно, со своим тестовым bridge.

## Что проверить

Для цепочек «принятый бонус → следующий шаг» источник прогресса — открытые движком Help, а не локальная кнопка или localStorage. Публичное задание содержит только начальные шаги и разрешённый справочник; будущие связи и ответы приходят с соответствующими Help. Каждый Help содержит читаемый запасной вариант шага, чтобы задание оставалось проходимым без JS. Обработчик выдерживает Help до загрузки задания, повтор, находку вне очереди, смену уровня и полную перезагрузку без утечки состояния между командами. Отдельно проверяйте сбор фрагментов и фактический зачёт составного ответа: раскрытие всех карточек само по себе не закрывает сектор.

Нулевая награда бонуса не означает нулевую длительность его доступности. В текст для игроков переносите правила поиска и ввода, а сведения о ещё не размещённых кодах и неподготовленных файлах оставляйте в авторском отчёте. После генерации моделью проверяйте эти смысловые различия до записи. Обрезанный модельный ответ (`finish_reason: length`) не является готовым планом: сохраните диагностику и usage до разбора, исправьте лимит/запрос; к записи переходите только после полной валидации.

Названия полей ввода в задании сверяйте с настройкой блокировки и фактическим preview по [правилу маршрутизации](scenario-mechanics.md#поля-ввода-и-блокировка), одинаковому для Legacy и Modern. Без блокировки пишите «общее поле ввода кодов»; при включённой блокировке проверяйте секторные и бонусные коды через соответствующие отдельные поля. В изолированном стенде внешние изображения заменяйте локальными fixtures и явно отмечайте эту подмену; доступность настоящих изображений проверяется отдельно на целевой странице.

До многошагового теста установите, накапливает ли выбранный авторский preview прохождение: после ввода второго бонуса проверьте наличие обоих открытых Help. На проверенном `tech.en.cx/admin/games/levels/preview` второй ввод заменял первый результат; reload POST повторно показывал последний код и сам по себе не доказывал сохранение прогресса. В таком режиме отдельно проверьте серверное принятие каждого бонуса/сектора и отдельно накопление/перезагрузку в стенде с полным снимком Help. Отчёт различает эти доказательства; localStorage не должен имитировать отсутствующий серверный зачёт.

1. Порядок появления авторского HTML, библиотек, runtime движка, заданий, подсказок и сообщений.
2. В каком контейнере находится скрипт и в каком — целевой DOM.
3. Область поиска селекторов: `document`, контейнер уровня или локальный корень виджета.
4. События загрузки и повторной отрисовки: `DOMContentLoaded`, `load`, ready handlers, MutationObserver.
5. Поведение после прихода подсказки/сообщения и после повторного открытия уровня.
6. Реакцию на ввод через штатную форму/bridge только в preview, включая открытие бонусного Help и выполнение его скрипта.
7. Ошибки console, отклонённые Promise, CSP/CORS, смешанный контент и недоступные ресурсы.
8. Mobile viewport, touch, клавиатуру, scroll и отсутствие перекрытия штатных элементов.

Не считай совпадение селектора достаточным, если элемент создаётся позже или находится в другом payload-контейнере. Не меняй глобальные прототипы и не перехватывай штатные формы без необходимости.

## Результат

Укажи:

- точный preview target и проверенный уровень;
- шаги воспроизведения;
- ожидаемое и фактическое поведение;
- доступные console/network ошибки; если среда их не предоставляет, отметь ограничение наблюдения;
- какие браузеры/viewports проверены;
- что осталось непроверенным.

Если browser tool недоступен, подготовь код и план проверки, но явно пометь runtime-поведение непроверенным.
