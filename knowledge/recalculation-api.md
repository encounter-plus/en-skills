# Источники и контракт пересчёта

Движок выбирается реестром доменов до запроса. Modern использует SDK ниже; legacy использует авторизованную cookie-сессию и фиксированные native recipes. Ошибка авторизации не переключает движок и не разрешает bearer fallback.

## Legacy

`/gamestatistics/full/{gid}?json=1` читается внутри host. В модель и evidence попадает только allowlist Game/Levels/StatItems; пользовательский профиль, email и остальные поля JSON отбрасываются. `Game.Finished` задаёт завершение, `GameTypeID` — mode. `PagerVisible=true`, неизвестные IDs, неполный roster или изменившиеся данные останавливают чтение. `StatItems.Corrections` не содержит всех ручных корректировок: это не итог и не доказательство отсутствия начислений.

Принятый roster читается со всех страниц `/GamePlayers.aspx?gid={gid}&status=1`. Team/user ID берётся из ссылки участника, настоящий game-player ID — из `player` ссылки действия в этой же строке. Ссылка действия только разбирается; не вызывается. Список options формы корректировки отдельно доказывает допустимость native получателя. Опция с числом сама по себе не устанавливает его identity. Время вступления в игру не выдумывается; для среднего автор явно подтверждает состав на cutoff.

Итоговый источник — HTML `/GameStat.aspx?gid={gid}`: native `data-v`, `data-c`, `data-lvl` и колонки `data-total=raw|corr`. Колонки сортируются независимо: сопоставлять их можно только по native ID, а не по позиции строки. Текущая схема final-total codec подтверждена для командного GameStat; неизвестная схема индивидуальной таблицы останавливает полный снимок. Это ограничение codec, а не запрет legacy-домена. Ручное начисление проверяется по ledger и точному read-back формы; затем отдельно проверяется изменение `corr` относительно сохранённого итогового baseline, при неизменных raw totals и прежних записях ledger. Нельзя дважды прибавлять StatItems и ledger.

Мониторинг читает обе вкладки и все страницы с сохранением multiplicity. Native action ID отсутствует; `legacy.eventIdentity=snapshot-local-index` явно помечает локальные опорные номера в конкретном снимке. Это не серверные IDs. Системные timeout-строки не становятся кодами. Timestamp мониторинга переводится в epoch только после чтения именно «Начало игры», проверки явного UTC offset и совпадения с native `StartDateTime.Timestamp`; персональная строка «в вашей временной зоне» не используется. Native `ActionTime.Value` сохраняет миллисекунды, `Timestamp` независимо проверяет epoch seconds.

Полнота устанавливается после повторного чтения всех страниц мониторинга, статистики, итогов и границ roster; это последовательный проверенный снимок, не атомарная транзакция. Legacy редактор может оставаться частичным: calculation требует наблюдённые answers/sectors/bonuses и полную manager state, сохраняет остальной uncovered scope. Авторские credit units/порог/историческое состояние задаются явным rule. Недоступная коллекция не превращается в пустой массив.

Перед native записью проверяются hash таблицы, сессия, свежие источники и observed revision ledger. Формы отправляются один раз, неизвестный результат сверяется чтением. Revision — обнаружение устаревшего снимка, не серверный CAS. Подтверждение плана, lock и журнал те же, что у modern. Снятие уровня использует native manager confirmation и независимый read-back состояния; проверка эффекта снятия на итоговые native totals пока возвращает unknown.

HTTP выполняется через `@encounter-api/sdk`. Generated группы `GamesMonitoringApi`, `GamesStatisticsApi`, `GamesPlayersApi`, `GamesResultsApi` задают routes/query/request serialization. Author adapter ограничивает origin `https://api.en.cx`, домен `*.en.cx`, заголовок `X-En-Client: automation`, хранение токенов, отсутствие повторных POST, session fence и размер ответа. Секреты и произвольные тексты ошибок не возвращаются модели.

Полные raw JSON хранятся как evidence. Generated DTO — typed projection: преобразует snake_case в camelCase и не сохраняет неизвестные поля/различие null и отсутствия. Передача wire `game_player_id` в generated request с `gamePlayerId` ошибочна; используйте API клиента, а не ручную сериализацию.

## Чтение

- `/games/{id}/monitoring`: обе вкладки, `type_answers=0`, `unique=false`, все страницы. Основной ответ содержит `answer_date_time`, `answer`, `is_correct`, `sector_id`, `is_level_pass`, `pass_type_id`, IDs. Бонусный содержит `enter_date_time`, `bonus_id`, verdict и IDs, но не полученную сумму. Ключ ввода — `(tab,action_id)`.
- `/games/{id}/levels/{level}/statistics`: номер уровня, не DB ID. `spent_seconds` — исходная длительность, `enter_date_time` — завершение; начало = завершение минус исходная длительность, как в Kotlin-приложении.
- `/games/{id}/statistics`: все страницы, `level_corrections` учитываются отдельно один раз. В серверном знаке положительная correction — бонус, отрицательная — штраф; скорректированное время = исходное минус correction. Закрытая/маскированная статистика или needs_confirm требуют отдельного процесса доступа.
- `/games/{id}/players`: полный roster с проверкой can_view; `/corrections`: items, players с обоими видами ID получателя, rights и временной режим.
- `/admin/games/{id}/levels/{levelId}/editor`: DB ID, version, состояние dismissed, ответы, секторы, бонусы и фактическое условие зачёта. Оно определяет units и required; число aliases не равно числу кодов.

Счётчики страниц сверяются, дубли/неизвестные IDs/неполные коллекции отклоняются. Отсутствующий timestamp/вердикт не равен нулю/false. Исторический фикс, цепочка и уничтожение не восстанавливаются из нынешнего редактора автоматически.

## Запись

`GamesResultsApi.postGamesByIdCorrections` создаёт временную коррекцию: `gamePlayerId`, `playerId` (team/user ID), `levelId`, `isBonus`, абсолютные `seconds`, `comment`. `score` для этого процесса отсутствует. Человеческая таблица и payload связаны SHA-256; изменение любой цели, суммы или комментария инвалидирует подтверждение.

Перед записью заново читаются влияющие данные. API corrections не предоставляет `base_version` или серверную идемпотентность. Host использует lock и устойчивый журнал, сохраняет unknown до dispatch. Ответ создания — integer map с незаданным именем ID: принимается только единственный однозначный ID, затем `/corrections/{correctId}` сверяет game/level, recipient, знак, величину и comment. Неудачный read-back после POST означает unknown.

При неопределённом результате дальнейшие записи останавливаются; verify сверяет ID или единственную новую относительно before-снимка запись с точными scope/получателем/суммой/причиной. Неоднозначные совпадения остаются unknown. Приватный журнал связывает correct IDs с incident ID; игровой comment содержит ровно причину, без служебных маркеров. Повторное apply того же плана возвращает журнал без повторной отправки. Для остатка нужен свежий расчёт с прежним incident ID и тот же store, затем новое подтверждение.

Снятие уровня использует `/admin/games/{id}/levels/{levelId}/dismiss` и проверку `level.dismissed`. После любых корректировок отдельно проверить статистику: verified записи не доказывает обновлённый итог, пока он не прочитан и не сопоставлен.
