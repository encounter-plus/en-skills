# Общий план импорта и восстановление

Используйте этот процесс из game-import и game-author при переносе сценария или оформлении существующих уровней. Инструменты выполняют запись; этот документ задаёт порядок и критерии завершения.

## Подготовка

1. Прочитайте GAME.md и исходную таблицу целиком. Разделите блоки на player-content, author-requirement, reference и excluded. Сохраните точные названия, ответы, диапазоны источника и требования к оформлению. Авторское указание не становится текстом задания.
2. Для существующего уровня вызовите encounter_inspect_import_level. Включите targetLevelId и возвращённый expectedResources в план. Чтобы заменить задание, укажите его прочитанный targetTaskId. Без этого ID добавляется новое задание; остальные задания сохраняются. Сектора/бонусы с совпавшим названием и другим содержимым требуют отдельного решения, автоматически не заменяются.
3. Подготовьте единый encounter_prepare_import_plan: schemaVersion:1, domain, gameId, request, sources, levels, необязательные assets и organizer, unresolved. В unresolved входят только невыполнимые требования внутри согласованного объёма. Исключённые разделы и настройки, которые автор просит сохранить, туда не входят.
4. Сопоставьте план с исходным запросом: все нужные названия, реплики, ответы, тайминги и оформление представлены. При unresolved запись не начинайте. Исправлять план после частичной записи новым planRef для обхода журнала нельзя.

## Состав уровня

Каждый уровень: key, name, sourceKeys, task:{text,sourceKeys,replaceNlToBr}, settings:[]. Дополнительные задания — additionalTasks с той же структурой. Для заданий допустим forMemberId из прочитанного списка получателей; по умолчанию 0 (все). targetTaskId заменяет конкретное существующее задание.

Необязательные коллекции:

- sectors:[{key,name,answers:[точные строки]}]. Первые 10 ответов создаются вместе с сектором; остальные добавляются отдельными журналируемыми шагами (до 200 ответов на сектор). Строки ответов не нормализовать.
- bonuses:[{key,name,text,help,answers,rewardSeconds,isNegative}]. Бонус привязывается к текущему уровню, получатель — все. Индивидуальные бонусы пока не поддержаны.
- hints:[{key,text,timeout,isPenalty}]. timeout в секундах. Для штрафной подсказки обязательны penaltyComment, penaltyTime, requestPenaltyConfirm. Получатели — все.
- messages:[{key,text}] — сообщения только текущего уровня; общий organizer распространяется на все уровни.
- settings: autopass с полными timeout/penalty hours/minutes/seconds и penalty_enabled; completion с all_sectors и required_sectors_count, если all_sectors:false. Условие завершения применяется после секторов.

Пропущенные коллекции и поля сохраняются. Сущности добавляются или переиспользуются только при точном совпадении. Произвольное удаление в этот процесс не входит.

## CSS, изображения и вложения

Ресурсы используют общую логику, отдельного скилла нет. В assets укажите {key,filename,mime,encoding,content,sourceKeys}. CSS: расширение .css, mime text/css, encoding utf8, content — готовый CSS. Изображения PNG/JPG/GIF: соответствующий MIME, encoding base64, content — канонический base64 реального файла. Максимум 10 MiB; остальные форматы пока неподдержаны.

В HTML используйте {{asset:key}}. Например organizer:{sourceKeys:[ключ требования],text:'<link rel="stylesheet" href="{{asset:dialog-css}}">',allLevels:true}. Для изображения: <img src="{{asset:photo}}" alt="…">. Исполнитель загрузит файл с хешем в имени, проверит байты по фактическому URL и только затем подставит ссылку. Названия CSS-классов должны соответствовать HTML диалога.

Нативная загрузка доступна Node legacy host при однозначной multipart-форме загрузчика и одном наблюдаемом адресе хранилища игры. Другой загрузчик возвращает явный блокер; endpoint или поля формы не угадывать. Встроенный CSS не заменяет требование загрузить файл.

## Выполнение и сбои

Вызовите encounter_create_level_from_plan для каждого key по порядку, используя авторизацию всего плана. Исполнитель пишет журнал до каждого побочного эффекта и проверяет версии существующих ресурсов. Runtime требует Node.js 24+: блокировка SQLite освобождается ОС при падении процесса, а записанные намерения остаются в JSON-журнале. Старый ownerless .lock не удаляется автоматически: перед удалением точного файла хост должен подтвердить остановку прежнего процесса.

При unknown/dispatching вызовите encounter_reconcile_import_plan. Он читает движок и исправляет только локальный журнал. Точное подтверждение записи позволяет продолжить тем же planRef. Отсутствие результата после таймаута не разрешает повтор: запрос ещё мог выполниться. Потерянное создание уровня без квитанции нельзя приписать единственному новому ID автоматически — нужна явная проверка автором. После неё передайте attribution:{levelKey,levelId,authorConfirmation} в reconcile; инструмент проверит единственный новый пустой ID и сохранность исходного списка. Исходное разрешение импорта не является подтверждением этой привязки. Не удаляйте журнал и не создавайте новый план для обхода остановки.

Ошибка чтения до отправки не отравляет журнал. При conflict/rejected исправьте конкретную причину; устаревший план для существующего содержимого требует нового согласованного снимка, а неопределённая предыдущая запись — сначала восстановления.

## Завершение

Вызовите encounter_verify_import_plan. Complete означает совпадение поддержанного содержимого с планом, включая ресурсы и зависимости; это не доказательство правильного толкования источника или визуальной вёрстки. Отдельно сравните результат с таблицей и требованиями, проверьте HTML/CSS в превью. Сообщайте фактические частичные результаты и оставшиеся ограничения. Обновите GAME.md по общему контракту памяти игры.

## Границы этапов

Чтение даёт реестр выбранных блоков с источниками и ограничениями. План даёт соответствие каждого блока объекту, исключению или нерешённому требованию. Для выполнения unresolved должен быть пуст в пределах согласованного объёма, а разрешение относится к конкретной версии плана. Сверка завершает каждую операцию только подтверждённым результатом; неизвестный исход требует чтения состояния, а не повторного POST. Эти границы описывают существующий протокол и не вводят новых машинных статусов.
